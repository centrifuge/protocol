# Vault Development Kit specification

This is the behavioral specification of `src/vaults`. Each row states a property the vault stack is
designed to uphold, at the granularity a reader can check against the contracts. Together the rows
define what the vault guarantees, what it deliberately does not, and where each guarantee is
enforced.

Read it as normative. If the code and a `y` row disagree, that is a bug in one of the two, and the
disagreement should be resolved rather than documented. Rows marked `n` are equally normative: they
record properties a reader might reasonably expect that the vault does **not** promise, so that
integrators and reviewers can see the boundary of the guarantee rather than infer it.

Scope is `src/vaults`: the vault, its settlement libraries, the request transport, the hub-side
request manager and its reference wrapper, and the policy implementations. It composes with (and
does not restate) the properties of `src/core` and `src/token`, specified in the protocol-wide
[`docs/SPECIFICATION.md`](../../docs/SPECIFICATION.md), whose vaults section points here. Where a
vault property depends on a core one
(escrow accounting, exactly-once message delivery, transfer-hook enforcement), the Notes say so.

## How to read a row

* **Invariant**: the property, stated so it can be checked. One property per row.
* **Holds**: `y` if the stack upholds it on the current contracts. `n` if it deliberately does not
  (intended behavior) or is a known, acknowledged break. Every `n` carries its rationale in Notes;
  treat them as documented non-guarantees, not defects.
* **FV**: where the property is formally verified. `-` everywhere today: there are no Certora specs
  for `src/vaults` yet, so this column doubles as the work list for a first FV pass.
* **Tests**: the test exercising the property today, by file under `test/vaults` unless stated;
  `BasinLiability`, `Deployer`, `EndToEnd`, `FundOfFundsBasin`, `FundOfFundsRegressions`, `OrderBookBoundary`,
  `SecurityRegressions`, `VaultLocalDeploy`, `VaultRouter` and `VaultSettlementEvents`
  are under `test/integration`; `MathLib` is under `test/misc/unit/libraries`. `-` means nowhere. This column deviates from the protocol-wide spec,
  which tracks a `Fuzz` column against the recon suites: here it names unit tests, the property
  fuzzing inside them and the stateful invariant suites (`BucketLibInvariants`, `VaultInvariants`,
  `VaultPricingLibInvariants`). The protocol-wide recon suite in `test/integration/recon-end-to-end`
  also drives the VDK end to end, and is cited by property name where it is the coverage. A row with `-` in both FV and Tests is still part of
  the specification; it is simply unverified, and is a candidate for a future spec or fuzz property.
  A named test means that test exercises *that* property, not merely that it touches the contract, so
  a `-` next to an obviously-important row is a real gap. On an `n` row a named test pins the
  documented non-guarantee rather than the property.

The ERC-7540/ERC-4626 conformance rows were cross-checked against the property set from the Cyfrin /
alexzoid formal-verification report on Accountable Credit Vaults (October 2025), which verifies an
async-redeem vault against 16 EIP-7540 and 40 EIP-4626 rules. Where that vault is stricter than this
one the difference is deliberate and recorded: it enforces an owner-or-operator check on
`requestRedeem` (ERC-7540 mandates supporting the ERC-20-approval flow instead), and it is fully
async so its previews always revert, which a dual-mode vault cannot do.

## Vocabulary

A **bucket** is the unit of async settlement, keyed by a 96-bit **localId**. Every request is a
**contribution** to a bucket; the **request policy** chooses which. A bucket's **total** is the
pro-rata denominator. **Flushing** sends a bucket's queued amount to the request manager and closes
the bucket to new contributors; a **sole owner** (a contributor who owns the whole bucket) may keep
extending it afterwards. **Folding** moves a contributor's settled pro-rata slice out of the bucket
into their per-controller claimable ledger.

A **requestId** is the vault-namespaced id the hub sees: `(vault address << 96) | localId`. The
**request manager** is the per-pool contract registered in the SpokeRegistry that the vault sends
requests to and accepts settlements from; the default is `VaultRequestRouter`, which forwards to the
hub, but a pool may register one that settles locally.

A controller is in **async mode** when they have anything claimable or a request pending, and in **sync
mode** (instant) otherwise; the 2-argument ERC-4626 entrypoints route on that distinction. Only the controller,
its operator or a **sponsor** (a payer the vault's instant policy accepts, from a per-vault list the pool sets) can credit a
controller a request, and on a vault with an instant lane a transferred position too. A sponsor funds a position
without any say over its claims. On a vault without an instant lane a transfer is a plain ERC-8161 push. A cancellation
carries two amounts: **gross** retires the pending request and releases its reservation, **net** is
what the investor may claim; the difference is a retained fee.

A price is **set** when the hub has notified it at least once. Registry validity means *set*; the
oracle adds an optional **freshness** bound on top of it (`SpokeOracle.maxAge`, fixed at deployment).

## Deployment model

Every contract in this stack outside the vaults themselves is a **per-network singleton shared by all
pools**: `VaultFactory`, `VaultRequestRouter`, `SpokeOracle`, the request policies (one instance per
configuration), `ReserveInstantPolicy`, `VaultLiquidityRoute`, and hub-side `OrderBook` and
`FeeRequestManager`. `BasinLiquidityRoute` is one per venue, shared by every pool that draws on it. A vault is per position; the
things it points at are not. That is a deliberate choice, and it makes "which pool is this call for"
a security boundary rather than a bookkeeping detail, because several of these hold manager rights on
every pool that uses them.

Three properties carry that weight, and each is asserted in the rows below:

* **State is keyed by pool or by vault.** Orders are `[poolId][scId][assetId][requestId]`, fees
  `[poolId][assetId]`, observers `[poolId]`, policy state `[vault]`. Nothing is keyed by a share class
  or a local id alone, so one pool's writes cannot land in another's slot.
* **Callers are checked against the pool they claim.** The Spoke gates every balance-sheet call on the
  caller being a manager of that pool, `spoke.request` on being that pool's registered request
  manager, and the policies on `vault == msg.sender`.
* **Identity comes from the registry, never from a caller-supplied address.** `vaultDetails` is the
  sole authority on which pool a vault belongs to. A contract asked `poolId()` directly can answer one
  way while a configuration call is validated and another once it is acted on, which is exactly how a
  manager of one pool would reach another (`CrossPoolIsolation`).

The isolation tests are therefore load-bearing rather than defensive: with singletons, they are the
argument that a manager of pool A cannot touch pool B.

## Trust in pool-chosen components

The request and instant policies, the liquidity route, the oracle, the settlement observer, the share
token's hook and the OrderBook's request observer are the pool's choice, and the stack calls them
plainly: no gas caps, no fallback values, no ceilings applied over their answers. The exceptions guard a
view or a conversion rather than an answer: a capacity is clamped to what converts, a rebate to zero in a
quote, and each underlying's quote in `VaultLiquidityRoute` to `QUOTE_GAS`, the one place the stack caps gas. A component that
reverts, burns gas or misreports harms that pool's own users, not other pools or the protocol. Where
an actor the pool did not choose can reach a path (another pool's vault behind `VaultLiquidityRoute`,
a third-party venue behind `BasinLiquidityRoute`, an investor, a keeper), the
stack catches ordinary reverts instead of capping gas. Gas a component needs is priced in `GasService`
or funded by the pool through extra gas, never capped in a contract apart from that one quote.

## Deployment constraints

Three `n` properties in the tables below are `n` not because the code is wrong but because the safe configuration cannot
be enforced from inside a vault whose features depend on the permissive one. A pool is expected to
satisfy all three.

1. **A restricted share class is gated by its own hook.** `requestRedeem` must support the ERC-20-approval
   flow, and the share leg it uses is an authorized transfer that the token's transfer hook does not
   observe. The vault therefore asks the share token's current hook the role checks of every vault action, so
   the gate cannot be left off a vault, and a hook without the `IRoleHook` surface fails closed. That authorized
   transfer is the share token's registrar `authTransferFrom`, which `IRegistrar` makes an optional capability
   with no way to ask for it. The vault also burns shares through it (the redeem settlement, a redeem
   cancellation and the instant exits), so a share class whose registrar lacks it cannot serve async or
   instant redemptions, and its `requestRedeem` and `revokeShares` revert. Deposits are unaffected. Check the
   registrar before linking a vault to a share class.
2. **An instant lane needs a price-freshness bound.** Registry validity only means a price was notified
   at least once. A vault configured with an instant policy should use an oracle with a non-zero
   freshness bound (the canonical `SpokeOracle` is deployed with a `maxAge` of 1 day), or supply one
   that bounds age itself. The same holds for the gap between the asset and share prices: `SpokeOracle`'s `maxSkew`
   bounds it, and zero leaves it unbounded. The canonical oracle sets it equal to `maxAge`, where it adds no bound
   of its own, since two prices each within `maxAge` of now are within `maxAge` of each other; a tighter pair
   needs an oracle deployed with a smaller `maxSkew`.
3. **A shared liquidity route is shared across pools.** The venue's liquidity is not reserved per
   vault, so every vault enabled on one liquidity route draws on the same venue, including vaults of
   other pools. A pool cannot be starved into insolvency by this (a draw that cannot be met reverts,
   and the payout is bounded by the escrow reservation either way) but its instant-exit capacity is
   only as reliable as the behavior of every other pool enabled on the same route. Per the
   deployment model above a route is a singleton, so the answer is not a second instance but a
   credit line per vault: `BasinLiquidityRoute` bounds each vault's outstanding receivable by the
   lower of a limit its pool sets through the Envoy and a credit the venue's liquidity provider sets
   directly, so the venue consents to every pool that draws on it and bounds what each may owe. What
   it does not do is partition the venue: lines that together exceed the venue's liquidity are each
   quoted against the whole of it, and whoever draws first takes it. `VaultLiquidityRoute` has no such
   line: its venue is each underlying vault's instant lane, which sees the route as one caller for
   every pool, so the underlying's own pool consents to each routing vault by name instead (see the vault liquidity route section).

**Gas benchmarks assume the cancun schedule.** `GasService`'s benchmarks are taken with the bytecode the
chains run, compiled for cancun, executed under cancun, while every chain that can take vaults runs a later
fork (EIP-7907 at least). Prague executes the vault paths at the same price: the `EndToEnd` benchmark run with
`FOUNDRY_EVM_VERSION=prague` reproduces the cancun `requestCallback` measurement exactly. Osaka reprices nothing these
paths execute (its changes are MODEXP, a new `CLZ` opcode and the EIP-7825 transaction cap), and the pinned
toolchain cannot execute it or anything later, since solc 0.8.28 tops out at prague. What a later fork can
move is EIP-7907's own per-word charge for cold-loading code past 24,576 bytes (~0.7k for the vault, ~1k for
the factory on each cold call). It is not in the benchmarks and no reserve is added for it, a deliberate gap
at about 0.1% of a callback. The vault's deployment is not a message: it is a spoke transaction ahead of
`DeployAndLink` (see `VaultFactory`), paid by whoever sends it, so no benchmark depends on code deposit. A
message that runs short fails on the spoke and is retried with more gas rather than lost.

## System-level properties

Compositional properties spanning the vault, the transport, and the hub-side request manager. No
single contract enforces them alone.

| Invariant | Holds | FV | Tests | Notes |
|---|---|---|---|---|
| Request-id soundness: a settlement always lands on the vault that created the request, and no vault can address another vault's request | y | - | VaultRequestRouter | The router derives the requestId from `msg.sender` outbound and resolves the target vault from the requestId inbound, so the id is never caller-supplied on either leg |
| Request ids are globally unique across vaults on a network without any registry | y | - | VaultRequestIdLib | `(vault << 96) \| localId` partitions the id space by vault address. Uniqueness *within* a vault is structural for every policy: a policy names buckets by keys and the vault allocates the local ids from a counter, so ids are unique among live buckets; a key keeps its id, so `PerInvestorPolicy` reuses a retired one (see Request policies) |
| A request is funded at registration: assets (deposit) or shares (redeem) reach the escrow in the same transaction the request is recorded | y | - | Vault, EndToEnd | This is what forecloses unfunded commitments; see the deliberate non-guarantee in the Vault section |
| A locally-registered request manager cannot brick a position by settling out of order, beyond what was sent, or one-sidedly | y | - | BucketLib | All three obligations on whatever the pool registers as its request manager are enforced by the vault itself, because breaking any of them is unrecoverable: `settle` rejects an unflushed bucket (`BucketNotFlushed`), a settlement beyond what the bucket sent (`OverSettled`), and a non-zero leg against a zero one (`OneSidedFill`). `OrderBook` enforces the last two hub-side as well, where they fail the manager's call before a message is sent. The per-rule rows are in the BucketLib section |
| Settlement is fair within a bucket, and unordered across buckets | n | - | BucketLib | Within a bucket the split is floor pro-rata on `contributed/total`, and it is split-invariant: several calls in one window land in the same `localId` and simply increment the contribution, so a request cannot be split for advantage. Across buckets there is no ordering at all. Under `PerRequestPolicy` and `PerInvestorPolicy` every bucket has a single contributor, so pro-rata is vacuous and *which* request the manager fulfils is entirely off-chain discretion. Only `PerPeriodPolicy` gives a fairness property, and only among contributors who landed in the same window. Queue position is not a protocol concept here; a pool wanting one supplies it hub-side (a monotonic tag in the localId's static bits plus a frontier in the request manager) |
| A pending request is priced at fulfillment, not at request | y | - | Vault, EndToEnd | The price is a manager-supplied parameter to the fill, so a NAV movement between request and fulfillment accrues wherever the fill price puts it. A request pending across a write-down can therefore be filled at the pre-write-down price, which transfers value from remaining holders to the exiting one, and symmetrically a subscription can be filled at a stale price to the incoming investor's cost. The bound is hub-side (`StdHubPolicy.maxFulfillPriceDeviation`), a deployment parameter that `type(uint128).max` turns off. Integrators should not assume the ERC-4626 mental model of request-time pricing; ERC-7540 does not address it |
| Share price is a valuation, never a ratio of balances | y | - | Vault | Every conversion routes through the oracle's hub-notified prices; `totalAssets()` is `convertToAssets(totalSupply())`, a valuation rather than a measured balance, and instant capacity reads the escrow's internal accounting (`total - reserved`) rather than `balanceOf`. This is what makes the ERC-4626 inflation, donation and first-depositor family unreachable: a raw transfer to the escrow moves no price and no capacity, and there is no ratio for a first depositor to skew. It is also why there is no virtual-offset or dust guard here: the constructs those defend do not exist. Euler's stealth-donation generalisation (rounding dust accruing to the pool) does apply, but it closes only through a hub round-trip and a manual NAV recompute, so it is linear rather than compounding and accrues to all holders |
| Claimable backing (shares): shares credited to controllers' `maxMint` are covered by shares the escrow holds, because async issuance mints to the escrow and claims move escrow → receiver | y | - | EndToEnd, VaultInvariants, VaultGuards, SecurityRegressions | Composes with the core escrow properties. Scoped to the async path: an *instant* deposit mints straight to the receiver against assets pulled in the same call, so it never transits the escrow and never enters a claimable ledger. A cancellation's net may not exceed its gross (`NetExceedsGross`), so a cancelled redeem credits no more shares than its request parked |
| Claimable backing (assets): assets credited to controllers' `maxWithdraw` are covered by the escrow's `REASON_REDEEM` reservation, established atomically with the share burn | y | - | EndToEnd, VaultSettlementOrdering, VaultInvariants, SecurityRegressions | `revokeShares` reserves before the burn, so the payout is earmarked before it is claimable. Both paths that credit a payout (a redeem fill and a deposit cancellation's net) first require the escrow's holding to cover it on top of what the vault already owes under `REASON_REDEEM`: the instant lane can take the cash a fill was priced against while its callback is in flight, and the callback then reverts, retryable once the pool refunds the escrow, rather than credit a claim that competes with backed ones. Cash reserved for pending deposit requests counts, since it is in the escrow: see the next row |
| A settlement is refused only for cash that is not in the escrow, never for cash reserved for other pending requests | y | - | VaultSettlementOrdering | A pool that invests its subscription cash and nets the next window settles the redemption before the deposit funding it: every unit in the escrow is then reserved for that deposit and nothing is available, yet the fill lands. The reservation briefly exceeds the holding, which closes the balance sheet's withdrawals (`availableBalanceOf` is zero), every redeem claim on the holding (`Escrow.withdraw` requires the total to cover every reservation before it pays anyone) and the instant lane, except through a liquidity route, whose first draw also clears the over-reservation, until the deposit is approved. If that deposit is cancelled instead, its refund is re-reserved under the same check, so it waits: the cancellation callback reverts and is retried once the pool tops the escrow up, while the redemption keeps the cash it was credited against. Another vault's reservations on the same position are not counted; see the next row |
| Parallel vaults on one position cannot together reserve more than the escrow holds | n | - | - | `_reservePayout` counts only this vault's `REASON_REDEEM` reservation, and core `Escrow.reserve` does not bound the total, so sibling vaults on one (share class, asset) can over-reserve between them (the A-1 remainder). No funds move wrongly: a claim unreserves its own amount and `Escrow.withdraw` then still requires every other reservation covered, so while the reservations exceed the holding every claim on it waits, not only the later claimant, until the pool tops the escrow up. The same holds against pending deposits: a redeem payout is checked against the holding without them, so it can reserve past the holding while a deposit's cash is reserved, and every withdrawal of that holding then waits until a deposit leg or a top-up restores the cash. Counting siblings would need the position's vault set, which core does not keep |
| Quantitatively: summed over all controllers, `maxWithdraw` plus every unfolded redeem entitlement never exceeds the escrow's `REASON_REDEEM` reservation for the vault | y | - | VaultInvariants | The aggregate form of the row above, and the one worth proving: every credit to `maxWithdraw` is preceded by a reservation of the same amount (`revokeShares`, or the re-reservation on a deposit cancellation), and every claim consumes both together via `withdrawReserved`. Floor rounding means the sum of slices is at most the reserved total, never more |
| Cancelled amounts are claimable on the opposite side, and only once: cancelled deposit assets via `withdraw`, cancelled redeem shares via `mint` | y | - | VaultGuards | Why standard ERC-4626/7540 integrators recover manager-cancelled funds with no cancellation awareness. They are kept as refunds (`refundAssets`, `refundShares`) apart from the fills, taken first by `withdraw`/`mint`, so they never move the fill ratio a `redeem`/`deposit` converts at or the share figure a redeem restriction is vetted on |
| A retained cancellation fee accrues to the pool and is never claimable by anyone | y | - | BucketLib, VaultGuards | Deposit side: gross is unreserved and only net is re-reserved, so the retained cash stays in the holding. Redeem side: the retained shares (gross minus net) are burnt from the escrow when the cancellation lands, so they leave supply at once rather than diluting until a manager burns them. That burn is not in the benchmarked `GasService.requestCallback`: the shipped `FeeRequestManager` retains no cancellation fee, and a manager that does funds the burn through the cancellation's `extraGasLimit` |
| Exactly-once settlement is enforced within `src/vaults` | n | - | BucketLib | It is inherited from the core messaging guarantee, not enforced here: `settle` accumulates rather than being idempotent, and it rejects a duplicate only when the bucket is spent (`pending != 0`) or the duplicate would exceed what the bucket sent (`OverSettled`). A duplicate within that bound double-counts |
| Value conservation across a fulfil: the assets consumed from the order equal the assets released from reservation, and the shares issued to the escrow equal the shares credited to contributors plus floor-rounding dust | y | - | BucketLib, BucketLibInvariants, EndToEnd | Dust is unclaimable and stays in the escrow |
| Cross-vault isolation: an operation on vault A cannot change vault B's buckets, contributions, or ledgers, even for the same pool and share class | y | - | VaultIsolation | Per-vault storage plus disjoint requestId ranges; parallel vaults on one position are the motivating case |
| Bystander isolation: an investor-initiated vault operation moves tokens only between the controller/owner/receiver, the escrow, the fee source and recipient, and the configured liquidity route | y | - | VaultIsolation | The liquidity route belongs in the set: an instant redemption short of escrow liquidity draws from the venue into the escrow. No party outside that set is touched |
| An unsettleable bucket cannot block a controller's other claims | y | - | VaultGuards | Claims fold only the horizon, and a completed entry leaves it as its fold completes; one that never settles occupies a horizon slot until a newer position evicts it, and never blocks a claim of anything already folded |
| No number of open positions makes a controller's claims or views costlier | y | - | Vault, RequestPolicies, FoldHorizonGas | Claims fold only the auto-fold horizon (the vault's `foldHorizon`, fixed at deployment from the factory payload, at least the request policy's `maxOpenBuckets` (`InvalidFoldHorizon`) and with no upper bound, since it is the pool's choice. Unset, it is `maxOpenBuckets`, 1 for the shipped policies without a notice; a batching pool configures more (8 keeps a week of daily windows) so an investor requesting every window keeps closed but unsettled windows auto-folded. A larger horizon costs a claim per entry held, and a third party's gifts can fill the free slots: at 8 that bounds a claim near 0.9M and a view near 0.4M), and pending views read per-controller totals maintained on contribute, fold and transfer. `FoldHorizonGas` holds claims and views flat from 1 to 256 open positions on both policy shapes. A claim folds both sides' horizons: with 16 settled shared windows per side it costs ~1.7M (about 65k plus 103k per horizon entry), held under 2M, and the views ~0.76M (about 20k plus 46k per entry), held under 1M. A hub callback folds at most the one bucket it settles and scans nothing, so `requestCallback` carries no cursor reserve. Nothing caps how many positions a controller holds |
| Fold transparency within the horizon: a controller's `pending*Request` and `claimable*`/`max*` views count the horizon's settled-but-unfolded slices as claimable, so folding the horizon is not observable as a balance jump | y | - | Vault | The views net in `HorizonLib.unfolded`. A settled slice of a batch outside the horizon is pending until something folds it (`foldRequest`, permissionless), and the fold is observable as a move from pending to claimable. Exact, since the ledger keeps exact totals, except for one floor: on a shared redeem bucket, where each contributor's pending is their contribution less a floored settled slice, so the contributors' `pendingRedeemRequest` can sum to one share unit each above the bucket's pending. Pending is never claimable, so that dust is a view artifact, not a claim the escrow must back (`testSharedRedeemWindowPendingDustIsNotAClaim` in `test/integration/recon-end-to-end/CryticToFoundry.sol`) |
| A policy's pool binding comes from the registry, so no pool's manager can point a shared policy at another pool | y | - | CrossPoolIsolation, VaultLiquidityRoute, RequestPolicies | The Envoy is reachable by every pool's managers, and `ReserveInstantPolicy`, `BasinLiquidityRoute` and `VaultLiquidityRoute` are per-network singletons acting for each pool that uses them (the two routes as its balance-sheet manager), so which pool a vault belongs to is a security boundary. Each reads it from `spokeRegistry.vaultDetails`, never from the vault: the address is caller-chosen, and a contract can answer `poolId()` with one pool while the Envoy validates and another once the policy acts on it. The registry reports the zero pool for an address it does not know, so an unregistered contract matches no pool. What the registry binds is pool identity, not code: any pool can link any contract through its own vault factory, and such a contract matches that pool. So the binding stops a pool configuring another pool's vault, but anything a singleton reads from a linked contract at execution time (its `share()`, its quotes, what it claims to have paid) is that contract's pool's data, not the registry's; see the vault liquidity route |
| A settlement message is bound to the position it names, so no pool can settle another pool's vault | y | - | VaultRequestRouter | The router compares the callback's `(pool, share class, asset)` against the registry's record for the target vault. This is the *only* possible binding, not a second line of defense: the router is a per-network singleton registered as every pool's request manager, so a vault's `onlyRequestManager` check resolves to the same address for every pool and says nothing about which pool authorized the settlement. Before the check, a pool registering its own hub-side manager could send a callback for its own pool naming another pool's vault and have it applied. The vault's own pool has to agree with the registry's record too, since the registry only records what a `DeployAndLink` factory returned (see "A vault is known to the stack only under the pool it was built for") |
| Shares issued are bounded on-chain by the assets actually received | n | - | - | Same non-guarantee as the core spec: fill amounts and prices are manager-supplied inputs to `OrderBook`, and the vault trusts its registered request manager. Bounding is the pool policy's job (`maxFeeBps`, `maxRebateBps`, `maxFulfillPriceDeviation` on `StdHubPolicy`), each a deployment parameter that `type(uint128).max` turns off |
| An investor can always claim a fulfilled amount | n | - | VaultGuards | Claims need no link, so unlinking a vault to wind it down still lets every folded or horizon slice be claimed. Every claim pays through the Spoke as a call by the vault, so it also needs the vault to still be a manager of the pool: retiring a vault keeps the role until its claims are paid, and `UpdateManager(false)` before then freezes them with `NotManager` (EndToEnd covers both orders). What can still stop a claim is a settlement that has not reached the vault: `VaultRequestRouter` refuses callbacks to an unlinked vault (see the next row), and the share token's hook or freeze rules can refuse the claim leg |

## Vault (`src/vaults/Vault.sol`)

One flat contract holding all state, both flow directions and the shared surface. At 43,784 bytes of runtime
code it is over EIP-170 and under EIP-7907, so it deploys only on a chain that has activated the
latter, as does `VaultFactory`, which carries its creation code.

## BucketLib (`src/vaults/libraries/BucketLib.sol`)

The single async settlement model; the horizon (invariant 5) is `HorizonLib`, over the same state. Its six numbered invariants (denominator monotonicity, floor rounding, no under-fold, pending totals, the horizon, settlement counting) are the load-bearing spec; the rest
of the vault's correctness rests on them.

| Invariant | Holds | FV | Tests | Notes |
|---|---|---|---|---|
| Denominator monotonicity: a bucket's `total` only ever grows, and only grows while the bucket is open or the contributor is its sole owner | y | - | BucketLib, BucketLibInvariants | Invariant 1. `contribute` requires `!flushed \|\| c.amount == b.total`. Extending as sole owner is safe because their ratio stays 1 regardless of `total` |
| A settlement only lands on a flushed bucket, so no fulfillment is measured against a denominator that can still grow | y | - | BucketLib | `settle` requires `flushed` (`BucketNotFlushed`). This is what makes invariant 3 hold rather than merely being usual: settle an open bucket and a later contributor grows `total` under an earlier contributor whose folded snapshot was taken against the smaller one: their slice shrinks below what they folded, and every subsequent fold underflows. Since the vault folds on every claim, that controller's position becomes permanently unclaimable. The shipped policies cannot reach it (the vault flushes before the request is sent, so the hub can only answer a closed bucket); the guard binds a pool-registered local request manager, which settles with plain typed calls |
| Floor rounding: a contributor's settled slice is `fulfilled * contributed / total` rounded down, and the dust stays in the escrow | y | - | BucketLib, BucketLibFuzz, BucketLibInvariants | Invariant 2, and provable: `Σ floor(F·cᵢ/T) ≤ floor(F·ΣCᵢ/T) = F` given `Σcᵢ = T`, which `contribute` and `transfer` both maintain. So the escrow can always cover every claim, and the checked `uint128` cast in the slice cannot revert *because* `contributed ≤ total`: the one cast in the stack that rests on an invariant rather than a bound, and the first thing to prove formally |
| Redeem-side dust is recoverable | n | - | VaultNonGuarantees | `revokeShares` reserves the full payout under `REASON_REDEEM` but only the sum of floored slices ever becomes claimable, and the vault never unreserves that reason. The remainder stays reserved permanently, excluded from the escrow's available balance, so it slowly shrinks instant-redeem capacity. Bounded by well under one asset unit per contributor per bucket, and no value is created (the aggregate backing invariant still holds), but it is a monotone lockup. A share-denominated `redeem` claim takes one floored slice of the ledger and withdraws exactly that, so claims add no dust of their own. Acknowledged rather than fixed. The slice dust has no point at which it is known to be final, since a shared bucket never learns that its last contributor folded, and releasing the claim rounding means a second `unreserve` on every `redeem` claim to recover less than a unit. | The floor-rounding remainder of a completed contribution never reads as pending | y | - | BucketLib, VaultGuards | Slices floor, so a shared bucket cannot credit every contributor exactly what they put in. Otherwise the leftover would read as pending forever, and the routing predicate would close the controller's instant lane permanently. This is inflictable on a victim, since a request names a caller-chosen controller |
| No under-fold: the folded snapshot never exceeds the current settled total, so `settled - folded` cannot underflow | y | - | BucketLib, BucketLibInvariants | Invariant 3, a consequence of monotonicity plus the flushed precondition above: the denominator is frozen before any fulfillment for every contributor except a sole owner, whose ratio is invariant. Fuzzed over arbitrary interleavings of contribute/flush/settle/cancel/fold/transfer in `BucketLibInvariants` |

The `flushed` check says a settlement answers a request that was sent, but it is per-bucket, so on its own it stops only the first such settlement. ## Vault liquidity route (`src/vaults/liquidity/VaultLiquidityRoute.sol`)

An `ILiquidityRoute` for a fund-of-funds: a pool that holds positions in other vaults. It redeems
those positions on demand, so a top-level instant exit is paid out of whatever backs the underlying
vault, including that vault's own liquidity route, in the same transaction:

    top-level vault.redeem -> VaultLiquidityRoute -> underlying vault.withdraw -> its own route

| Invariant | Holds | FV | Tests | Notes |
|---|---|---|---|---|
| A route must be linked in the registry, paying out the top-level vault's own asset | y | - | VaultLiquidityRoute | Linkage proves the route's pool, share class and asset, not its code: any pool can link any contract through its own vault factory. | What a draw releases and what it accepts are decided by the registry and the escrow, never by the underlying | y | - | VaultLiquidityRoute, FundOfFundsRegressions | The share token released is `spokeRegistry.shareToken` of the route's registered share class, not the underlying's `share()`, which a contract its pool linked could point at any other token this pool holds. It is not measured at the escrow, which every vault of the pool deposits into: an underlying reentering a sibling vault's deposit would pass that off as its payout. | `available` is bounded by the vault's credit line | y | - | BasinLiquidityRoute, FundOfFundsBasin | `min(venue liquidity, min(limit, credit) - receivable)`, saturating at zero when either side lowers its limit below what is owed. Through `VaultLiquidityRoute` it is also the capacity a fund-of-funds vault above reports |
| A draw is owed by the pool of the vault that drew it, whichever topology | y | - | FundOfFundsBasin | `receivable` is keyed by the calling vault. Direct, the fund-of-funds pool owes the venue and its jTRSY position is untouched; composed, jTRSY owes it and the fund-of-funds pool's jTRSY position shrinks by the exit |
| A Basin draw is booked as the pool's liability in the same transaction | y | - | BasinLiquidityRoute, BasinLiability | `provide` mints liability accounting tokens (`AccountingToken`, id `toTokenId(pool, asset, true)`) equal to the draw and `deposit`s them into the vault's share class in the pool's escrow, beside the vault's `noteDeposit` of the cash; `repay` withdraws and burns the same amount, unless the route lost the roles to or the escrow no longer holds it (`BasinLiabilityLeftBooked`). The escrow's liability balance therefore moves with `receivable` while the pool's setup is intact (recon `property_basinDebtIsBooked`), and both deltas are queued before the exit returns. The snapshot queue marks no update a snapshot while any queued delta of the share class is unsubmitted, so a snapshot hook (`NAVManager`) never values the cash without the debt. With the liability holding configured hub-side, a draw leaves NAV per share unchanged: 100 of T-bills over 100 shares, a 10-share exit drawn from the basin publishes 90/90 = 1.000 rather than 100/90 = 1.111, and the repayment leaves it at 1.000. The token id is per pool and asset, not per vault or route, so any other minter of the pool (`OnOffRamp`'s in-flight liabilities) adds to the same holding; each removes only what it booked, so the totals stay additive |
| The hub nets a Basin draw from NAV without pool configuration | n | - | - | The route books spoke-side and cannot see the hub. Until the pool initializes the liability token as a liability holding (`NAVManager` `InitializeLiability`, or `initializeHolding` with a credit-normal liability account), the hub tracks its amount without value and NAV still overstates by what is owed; initializing it later books the amount already there. Initialized as an ordinary asset holding, it would add the debt to NAV instead. The liability is valued at the holding's valuation, so it matches the cash it paid for only if both are valued alike (the identity valuation for both, or the same price feed). Only the principal is booked: interest or fees on the line are hub-side pool expenses |
| A pool where the draw cannot be booked has no Basin capacity | y | - | BasinLiquidityRoute, BasinLiability | `available` is zero unless the route is a spoke manager of the vault's pool, a minter of its accounting tokens, and the liability token a registered spoke asset, so the vault's `max*` never advertise a draw that reverts. A draw without them reverts in the booking (`NotManager`, `NotMinter`, `UnknownAsset`), so a pool cannot draw unbooked. The pool's spoke policy cannot be asked in a view |
| `available` is a per-vault entitlement | n | - | BasinLiquidityRoute | The line is a bound, not a reservation: vaults whose lines together exceed the venue each see the venue's liquidity, and they need not belong to the same pool, so one pool's instant exits can consume liquidity another pool was counting on. Advisory by contract, so overstating it only makes the redemption revert, but see Deployment constraints |
| A surplus draw is accounted | n | - | - | If the venue returns more than requested, the excess lands in the escrow but is neither added to the receivable nor noted into the holding, so it reads as a donation |
| Repayment is permissioned | y | - | BasinLiquidityRoute | Only a spoke manager of the vault's own pool (`spokeRegistry.manager`) may repay, since repaying reopens the vault's line. Repaying also withdraws the booked liability as far as the route still can: a route without its manager or minter role, or an escrow whose liability balance another manager moved, still takes the repayment and reduces the receivable, leaving the rest booked (`BasinLiabilityLeftBooked`) for the pool to clear with its own roles. The payer is `msg.sender`, and the destination is fetched live from the venue on every call, so the venue can redirect where repayments go |
| Route and policy events carry the pool and a name no other contract under `src/vaults` shares | y | - | BasinLiquidityRoute, VaultLiquidityRoute, ReserveInstantPolicy, RequestPolicies, SpokeOracle | `SetLimit`, `SetCredit`, `SetRoutes`, `SetConsent`, `SetConfig`, `SetAllowed` and the draw, claim and repay events lead with `PoolId indexed poolId`, then `vault`. `BasinProvided`/`BasinRepaid`/`BasinLiabilityLeftBooked` and `VaultRouteProvided` differ from the vault's `Claimed`; `VaultRouteProvided` also reports `residualShares`, the part of the previewed `shares` returned to the escrow, so the shares burned are `shares - residualShares`. The constructors with configuration announce it: `PerRequestConfigured`/`PerPeriodConfigured` and `OracleConfigured` (with the registry and envoy); `SpokeOracle.SetPaused` fires only when the flag changes |
| Deposits are offered to the route for allocation | y | - | LiquidityRouteIntegration | Both deposit settlement legs offer the assets that just entered the escrow to the route through `forward`: instant issuance (`_executeInstantDeposit`, the amount the escrow receives) and async approval (`approveDeposits`, the amount just unreserved into the holding). A forwarding route auto-allocates them into its venue; a no-op route leaves them idle. The redeem side mirrors it: `provide` pulls the venue back in for an instant exit short of escrow |
| `forward` is optional | y | - | VaultLiquidityRoute, BasinLiquidityRoute | A route pulls what it wants and returns; a route that forwards nothing is a valid no-op that leaves the assets idle, and an un-forwarded amount is not an error. Both shipped routes are redeem-side only and no-op it |
| A liquidity route cannot stall settlement or the instant deposit lane through `forward` | n | - | LiquidityRouteIntegration | Deliberate: `forward` runs inside `approveDeposits`, a hub callback, and inside instant issuance, and is called plainly (trust in pool-chosen components), so a reverting route fails the callback, which the gateway keeps for retry, and the instant deposit. Its gas is not in `GasService.requestCallback`: a pool with a forwarding route funds it through the fulfillment's `extraGasLimit`. `provide` is plain too, since an instant redemption it cannot fund must revert |
| The cost of provided liquidity is priced by the route | n | - | - | Deliberate: priced as an exit fee by a composed instant policy, so the route stays a pure liquidity provider |

## Request id and wire libraries

`src/vaults/libraries/VaultRequestIdLib.sol`, `src/vaults/messaging/libraries/RequestMessageLib.sol`, `RequestCallbackMessageLib.sol`.

| Invariant | Holds | FV | Tests | Notes |
|---|---|---|---|---|
| `from(vault, localId)` round-trips: `vaultOf` and `localIdOf` recover both components exactly | y | - | VaultRequestIdLib | The two projections partition all 256 bits, so the round trip is total in both directions and every `uint256` is a canonical id; there is no invalid bit pattern to validate |
| Distinct `(vault, localId)` pairs never collide | y | - | VaultRequestIdLib | The packing is a bijection: the vault occupies the high 160 bits and the localId the low 96 |
| A localId cannot overflow into the vault field | y | - | VaultRequestIdLib | `localId` is typed `uint96` at every producer and validated by the ABI decoder, so a wider value cannot be smuggled in. A policy's own counter arithmetic is its own obligation |
| Every message type round-trips through serialize/deserialize | y | - | RequestMessageLib, RequestCallbackMessageLib | Field offsets are identical between each paired serializer and deserializer |
| An unrecognized message type is rejected | y | - | RequestMessageLib, RequestCallbackMessageLib | But not through the custom error: a type byte above the enum maximum panics on the enum cast, and the `Unknown*Type` errors are reachable only for a type/variant mismatch or the zero variant |
| A truncated payload is rejected | y | - | RequestCallbackMessageLib | The byte-slicing helpers bounds-check and revert `SliceOutOfBounds`, so a payload shorter than its type requires cannot be misread |
| An encoding is unique | n | - | - | Deserialization reads fixed offsets and does not check the exact length, so trailing bytes are ignored: several byte strings deserialize to the same message. The messaging layer produces the encodings, so the consequence is narrow: a byte-level equality check is not a valid message-equality check |
| The type byte is the only discriminator between same-length messages | y | - | RequestMessageLib, RequestCallbackMessageLib | The four 65-byte callback variants (`SettledDeposit`, `SettledRedeem`, `CancelledDeposit`, `CancelledRedeem`) are byte-identical apart from that byte, which is what separates a settlement from a cancellation and a deposit from a redeem, and the two 49-byte requests likewise. Every deserializer re-checks it, so a mismatch fails rather than being reinterpreted |
